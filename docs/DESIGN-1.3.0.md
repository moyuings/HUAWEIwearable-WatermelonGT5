# 1.3.0 当前设计

目标为 GT5、466×466 圆屏、API12。512 KiB 是采用的 JS 堆预算，不是本轮测得的 GT5 容量。当前 SDK、预览及设备证据以 VALIDATION.md 为准。

## 物理和调度

使用预分配的 40 槽 SoA 数组。物理对象不进入页面 data。圆形重力、墙壁、地面、同级合成、同一步单次消费、40 颗容量上限和失败宽限保持原规则。无浏览器 Canvas、DOM、requestAnimationFrame 或大型第三方物理运行库。

x 轴扫描与 y 轴拒绝先筛出候选对；保留上一轮排序顺序，增删对象后重建，随后用插入排序校正。每物理步最多 4 遍求解；只有没有任何位置、速度、墙壁或合成变化时才提前结束该步的剩余求解遍。全场静止休眠沿用旧版，不是此次新增。

固定物理时间步 1/60 秒。30/60 模式只改变目标更新节奏，物理参数不随模式改变。每次最多补 6 步，最多接纳 100ms，超额时间计入 discardedMs；游戏线程卡顿时不无限追赶。原生重复定时器请求 32ms/15ms，实际更新由 1000/30 或 1000/60ms 截止时间约束，只有一个活动游戏循环。没有伪造经过时间来增加帧数。

## 显示对象与内存上限

HML 使用固定 40 个数字槽号，一次构造、跨投放/合并/重开保持数组引用。每槽一张直接 image，空槽通过 show 隐藏，移除旧版每槽的全棋盘 stack 包装。物理有 40 槽、响应式投影有 40 个小对象、非响应式比较缓存有 40 个小对象。源码和对象计数不能代替实际堆测量。

每次集中比较普通 JS 缓存，只向响应式数据写入变化字段。没有每颗水果单独计时器、每帧文件读写、全场 JSON 序列化。页面仍有固定 UI 控件、一个受限合成环；不添加粒子系统。

此前尝试的“每次增删水果后重建活动图片数组”在官方 SDK、512KiB 堆中第二局出现 JS HEAP OOM，已撤回；证据位于 experiments/。这说明短时预览通过不足以验证该方案，不能据此断言原版 GT5 470 分故障具有相同根因。当前方案的实际长测数据见验证记录。

11 张水果图尺寸 18～116 像素，压缩 PNG 合计 87,130 字节；单份 RGBA 解码估算 197,696 字节。114/80 启动图标额外 77,584 字节。原生图片缓存是否共享、实际格式及图片池占用未测；图片池与 JS 堆分开讨论。512 母图只在电脑源码中，不打进 APP。

## 生命周期、保存和诊断

后台停止游戏循环、初始化与探针任务，回到同一实例可恢复局面；退出进程不承诺恢复完整棋盘。设置和最高分沿用原存储 key，成功回调后才提示成功。读取未知旧最高分失败时不覆盖为零。跨页面、超时和迟到回调有逻辑失效保护；原生存储的实际可靠性仍待 GT5 复测，未改造成事务型存档。

循环异常会停止任务、显示异常类别，并写入有界日志。已结束的局面不能从“继续”入口重新启动，只有重开才清空世界并建立新 round。round 事件用于确认实际重开，不把点击次数当成功次数。

日志最多 8 条、上下文最多 20 项、二维码最多 32 页；运行时进度每 10 秒或跨 100 分记录一次内存日志。持久化只在原有设置/暂停/结束操作发生，不在每帧写入。性能页面新增原生回调频率、最小正时间差及二维码中的重复时间戳计数。

loopHz 是执行更新频率，submitHz 是有变化的数据提交批次，callbackHz 是定时器回调频率。提交耗时仅覆盖 JS 调用，不覆盖异步原生绘制。最小正时间差是采样观察，不等于准确测得系统时钟分辨率。没有真实呈现帧计数，renderHz 保持 null。

## 构建和验证

保留 com.moyu.gt5.watermelon / moyu / API12 / default 入口 / 114 与 80 图标结构。通过官方 Hvigor 构建 APP，并把源码输入哈希、APP 哈希和预览快照哈希联系起来。独立 SDK JerryScript 快照编译要与包内一致。Node 测试、SDK 预览、GT5 真机分别报告，不以其中一层替代另一层。
