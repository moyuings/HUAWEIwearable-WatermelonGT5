# 1.3.0 验证记录

日期：2026-10-25。**这是待 GT5 回归的性能优化版，不是已证实修复真机卡死的版本。**

## 环境与证据边界

- Windows 本机，官方 DevEco Node v18.20.1、Hvigor assembleApp。
- SDK 路径 E:/DevEco Studio/sdk；本机 JS 组件声明 version 6.1.0.105 / apiVersion 23。工程及包内目标/兼容仍为 API12（50000012），不是把预览器当成 API12 GT5 固件。
- 官方 Lite Simulator，466×466 circle，配置 JS 堆 524288 字节；原生报告可用总堆 524280 字节。生产编译文件原样运行，无替身 storage/file 或测试用物理引擎。
- 每个场景实际加载的 app 与页面快照 SHA 均与本次 APP 一致。入口版本文字改正为1.3.0后单独重跑入口；长测直接加载的游戏页与app快照没有改变。报告保留当时全部快照哈希，未加载的入口快照可以来自文字改正前。三份最终包内快照均通过独立SDK编译比对；源码输入与APP哈希见build-source-proof.json。
- **GT5：未连接验证。**用户旧版报告空场 11～12Hz、5～6颗时低于10Hz、约470分卡死。当前固件/可用堆/图片池未知，此前用户报告固件6.0.0.32。SDK结果不能推翻用户反馈。

## 实际修改与主机测试

1. 持久排序与保守提前结束，减少重复碰撞准备工作；保留40颗上限、4遍上限与6次补步。
2. 固定40图片槽位直接显示，空槽隐藏，移除40个全棋盘包装容器；普通JS缓存比较，不反复读取响应式旧值。
3. 异常停止循环并可见提示；已结束局面不能继续启动。新局有round记录，实际重开后才算通过。
4. 增加回调Hz、最小正时差与重复时间戳诊断；30/60两个目标模式保留，未伪造屏幕FPS。

35组生产逻辑检查 + 8组专项检查全部通过（官方Node v18.20.1），见code-tests-1.3.0.log和runtime-optimization-tests.log。另有24场固定种子完整游戏、93984步与旧物理精确状态对照：排序比较59892871→9295405，减少84.48%；总求解遍数减少5.40%。这不是GT5速度提升百分比。

覆盖重叠圆、40球、槽位复用、合并单次消费、469→470及更高分合并、后台恢复、重复输入、30/60物理一致性、旧回调、存储失败和循环异常。长时间逻辑测试采用虚拟时间，不能算真机实跑。固定样本和测试替身只在电脑工具中。

## 撤回方案与测试器修正

动态活动列表实验在第二局约143秒出现SDK JS HEAP OOM（日志堆524280、峰值453160字节），因此撤回，改用固定槽位。原始证据在experiments/active-list-oom.log和json，属于较早源码哈希，不是当前APP。此证据不能证明原版GT5约470分卡死同因。

测试器曾把“安排重开点击”误计为成功，并在结束后继续投放、误点菜单；现改为结束后阻断旧手势，以SUIKA_ROUND和下一局活动指标确认。传图重连不再重复初始化输入计划。失败实验不计入当前通过结果。

## 最少量GT5回归

1. 先30模式投放到5～6颗，暂停打开性能记录，记录循环/数据/回调/时差；再切60重复。若仍约10Hz，运行一次空载计时对照并保留日志二维码。
2. 连续玩并至少重开两次；观察约470分附近、连续合成和高水果数量。若卡死，记录前一刻分数、数量和操作。本版尚未证实修复该真机故障。
3. 切后台再回来，退出重开检查最高分和30/60设置，确认存储成功提示；签名/安装、显示FPS及图片内存仍需真机确认。

运行时间增加、不同固件及不同输入仍可能暴露未覆盖问题。默认30模式保留；没有在60模式不足时静默降档。
